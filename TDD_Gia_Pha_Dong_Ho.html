1. Nguyên Tắc & Tổng Quan Kiến Trúc

Modular Monolith theo DDD: một tiến trình triển khai duy nhất, chia thành các bounded context ranh giới rõ ràng, giao tiếp nội bộ qua interface/domain event. Mỗi module theo Hexagonal (Ports & Adapters): domain thuần nghiệp vụ, application điều phối use-case, infrastructure hiện thực hạ tầng, api phơi bày REST/GraphQL.
  • Phụ thuộc một chiều: api → application → domain; infrastructure hiện thực các port do domain/application khai báo (Dependency Inversion). Domain không phụ thuộc Spring/JPA.
  • Ranh giới module giữ sạch để có thể tách microservice về sau nếu quy mô bùng nổ.
  • Bất biến nghiệp vụ (invariants) từ BA: xóa mềm bắt buộc · audit versioning · RBAC theo chi/ngành · danh xưng bằng rule engine cấu hình được · gửi thông báo bất đồng bộ có retry/DLQ.
  • CQRS nhẹ: tách read model (cache cây, báo cáo) khỏi write model để tối ưu truy vấn cây lớn.

6. Mô Hình Graph (Apache AGE)

Cây phả hệ lưu trong đồ thị AGE tên giapha_graph. Node Person (chỉ giữ id + vài thuộc tính tra cứu), cạnh mang loại quan hệ. Dữ liệu chi tiết vẫn ở bảng person.

-- Tạo cạnh cha→con SELECT * FROM cypher('giapha_graph', $$ MATCH (p:Person {id: $parentId}), (c:Person {id: $childId}) CREATE (p)-[:PARENT {type:'BIO'}]->(c) $$) AS (v agtype); -- LCA + khoảng cách đời phục vụ danh xưng SELECT * FROM cypher('giapha_graph', $$ MATCH path1 = (a:Person {id:$id1})<-[:PARENT*0..]-(anc:Person), path2 = (b:Person {id:$id2})<-[:PARENT*0..]-(anc) RETURN anc.id AS lca, length(path1) AS dist_a, length(path2) AS dist_b ORDER BY (length(path1)+length(path2)) ASC LIMIT 1 $$) AS (lca agtype, dist_a agtype, dist_b agtype);

Chiều cạnh PARENT là cha→con (đúng như câu CREATE ở trên: (p)-[:PARENT]->(c) đọc là "p là cha/mẹ của c"). Vì vậy khi đi ngược lên tổ tiên phải dùng mũi tên ngược <-[:PARENT*0..]-; *0.. bao cả chính nó. Kết quả (lca, dist_a, dist_b, collateral_degree, side, gender, is_elder) là input cho KinshipResolver tra kinship_rule.

Đính chính v1.1 — bản v1.0 viết truy vấn LCA theo chiều xuôi (a)-[:PARENT*0..]->(anc) và mô tả "cạnh PARENT hướng con→tổ", cả hai đều mâu thuẫn với câu CREATE ngay phía trên. Chạy thử trên Apache AGE cho thấy truy vấn cũ trả về 0 row với mọi cặp người — tức là engine danh xưng sẽ im lặng không tìm thấy quan hệ nào mà không văng lỗi. Bản đúng ở trên đã được kiểm chứng: với cây A→B, A→C, B→D, C→E thì LCA(D,E) trả về (A, 2, 2).

8. Luồng Nghiệp Vụ Chính (Sequence)

8.1 Thêm nhân khẩu + kiểm tra kỵ húy + duyệt

Member/BranchHead → API(POST /persons) → AddPersonService 1. AddPersonService.validateTaboo(name) # FR-1.6 kỵ húy └─ nếu trùng tên húy bậc trên → cảnh báo (cho phép ghi đè có xác nhận) 2. Nếu người tạo là Member (không đủ quyền duyệt): └─ tạo ChangeRequest(status=PENDING) → thông báo Trưởng chi → DỪNG 3. Nếu BranchHead/Council (trong scope): tạo Person (is_deleted=false) 4. 8.2 Tra cứu danh xưng (LCA + rule engine)

User → API(GET /kinship?from=A&to=B) → ResolveKinshipTitleService 1. treeGraph.lca(A,B) → (lcaId, distA, distB) # Cypher AGE 2. tính RelationFacts: genDelta, side(nội/ngoại), gender, isElder 3. ruleSetRepo.resolveFor(branch(A)) → hợp nhất DEFAULT→REGION→CLAN→BRANCH 4. resolver.match(facts) → "Bác họ" (hoặc theo cấu hình dòng họ) 5. cache Redis (key A:B) → trả KinshipTitleDto

8.3 Nhắc giỗ theo Âm lịch (bất đồng bộ, Zalo)

SchedulerJob (chạy hằng đêm) → GenerateRemindersService 1. LunarConverter: với mỗi Event, tính ngày dương của giỗ năm nay (nhuận/GMT+7) 2. sinh ReminderJob cho mốc 7/3/1 ngày (status=PENDING) Khi tới fire_at: 3. publish NotificationRequest → RabbitMQ (exchange=notify) 4. ZaloProvider.send(...) → thành công: log SENT → lỗi: retry (backoff) → hết hạn → Dead-Letter Queue 6. ghi NotificationLog (provider_msg_id, status, retry_count)

8.4 Yêu cầu đính chính → Trưởng chi duyệt (RBAC theo nhánh)

AuditLog.record(UPDATE, before, after); request.status=APPROVED 4. thông báo người yêu cầu

1. Xóa thành viên → person.softDelete() (is_deleted=true) — GIỮ node graph 2. Yêu cầu xóa dữ liệu cá nhân hợp pháp (người sống): └─ AnonymizeService: xóa Tầng 3 (SĐT/email/địa chỉ/ảnh), giữ vai vế phả hệ └─ AuditLog ghi hành động (không ghi nội dung nhạy cảm)

10. Bảo Mật & Phân Quyền (RBAC theo chi/ngành)

  • AuthN: Keycloak (OAuth2/OIDC) + social login (Google, Zalo). Backend nhận JWT, map keycloak_sub → app_user → person.
  • AuthZ 2 chiều: (1) Role (ADMIN/COUNCIL/BRANCH_HEAD/MEMBER/GUEST); (2) Branch scope — annotation @RequiresBranch + BranchScope kiểm tra ltree path đối tượng nằm trong nhánh được giao.
  • Phân tầng dữ liệu: filter ở tầng application/serialization theo is_alive + role + privacy_level (mục 10 BA).
  • Chống OWASP: validate input, Cypher/SQL tham số hóa, rate-limit, CORS, mã hóa Tầng 3 at-rest, không log dữ liệu nhạy cảm.

11. Vận Hành & DevOps

CI/CD
  • Pipeline: build → unit test → integration test (Testcontainers: Postgres+AGE, RabbitMQ) → scan bảo mật → build image → deploy.
  • Migration Flyway chạy khi khởi động (kiểm soát bằng baseline).
  • Frontend: build → test (Vitest) → E2E (Playwright) → deploy.
Quan sát (Observability)
  • Logs tập trung (Loki), metrics (Micrometer→Prometheus), tracing (OpenTelemetry), dashboard Grafana.
  • Alert: hàng đợi DLQ tăng, tỉ lệ gửi Zalo lỗi, độ trễ truy vấn cây.
Sao lưu & Phục hồi
  • PostgreSQL: pg_dump hằng ngày + WAL archiving (PITR).
  • MinIO: versioning + sao lưu định kỳ.
  • Diễn tập phục hồi (restore drill) theo quý.
Cấu hình & Scale
  • Backend stateless → scale ngang; session ở Redis.
  • Worker notification tách tiến trình → scale theo tải mùa giỗ.
